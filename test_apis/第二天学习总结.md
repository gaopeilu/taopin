## 一、TokenRefreshView 完整源码链路

### 架构层级

```
URL: POST /api/v1/users/token/refresh/
        │
        ▼
┌─── TokenRefreshView (SimpleJWT 库) ─────────────────┐
│                                                      │
│  permission_classes = ()           # 不需要认证      │
│  authentication_classes = ()       # 不需要任何认证  │
│                                                      │
│  post() → serializer.is_valid() → 成功 200          │
│        ↘ TokenError → InvalidToken → 失败 401       │
└──────────────────────────────────────────────────────┘
        │
        ▼
┌─── TokenRefreshSerializer ──────────────────────────┐
│                                                      │
│  refresh = serializers.CharField()      ← 必填字段   │
│  access  = serializers.CharField(read_only=True)     │
│                                                      │
│  validate():                                          │
│    1. 解析 refresh token                             │
│    2. 校验用户是否存在、是否活跃                      │
│    3. 生成新的 access token                          │
│    4. 如果 ROTATE_REFRESH_TOKENS=True:               │
│       → 旧 refresh → blacklist() 拉黑                │
│       → 生成新的 refresh token                       │
│    5. 返回 {"access": "...", "refresh": "..."}        │
└──────────────────────────────────────────────────────┘
```

### 核心配置

```python
# settings.py
SIMPLE_JWT = {
    'ROTATE_REFRESH_TOKENS': True,         # 刷新时轮换
    'BLACKLIST_AFTER_ROTATION': True,      # 旧 token 拉黑
}
```

## 二、第三方库 View 的返回格式陷阱

| 来源 | 成功返回格式 |
|------|-------------|
| 你项目的 View（RegisterView, LoginView 等） | `{"code":200, "message":"xxx", "data":{...}}` |
| SimpleJWT 的 TokenRefreshView | `{"access":"...", "refresh":"..."}` |

**第三方库的 View 不会走你的自定义响应格式。** 原因：你的 `{code, message, data}` 包装是在你自己写的 View 里手动构造的，或者是异常处理器拦截异常时加的。第三方库直接 `return Response(data, status=200)`，不受你的逻辑控制。

**断言时需要区别对待**：
- 你的接口：`json_data["code"]`、`json_data["data"]["xxx"]`
- 第三方接口：直接读 `json_data["access"]`、`json_data["refresh"]`

## 三、Token 黑名单机制

### 工作原理

```
第一次调用 refresh 接口
  → 生成新 access + 新 refresh
  → 旧的 refresh token 存入 token_blacklist_blacklistedtoken 表
  → 旧 refresh 永久失效

第二次用同一个旧 refresh
  → 查 blacklist 表 → 发现在黑名单中
  → 返回 401 "Token is blacklisted"
```

### 需要手动安装

```python
INSTALLED_APPS = [
    'rest_framework_simplejwt.token_blacklist',   # ← 必须加
]

# 然后 python manage.py migrate 创建黑名单表
```

**不安装的后果**：`refresh.blacklist()` 抛 `AttributeError` 被 `except AttributeError: pass` 静默吞掉，旧 token 可以无限重复使用。

## 四、有副作用的接口如何测试

### 问题

改密码、删数据这类接口会改变状态，如果用固定测试账号 `test111`，跑完一次后其他所有用例全部炸掉。

### 三种企业级方案

| 方案 | 做法 | 适用 |
|------|------|------|
| **临时账号** | 注册新账号 → 测试 → 丢弃 | 你现在用的 ✅ |
| **事务回滚** | `django.test.TestCase` 自动回滚 | 单元测试 |
| **Fixture 生命周期** | `yield` 前创建、`yield` 后清理 | 封装后用 |

### 临时账号模式

```python
def test_change_password(self):
    # 1. 注册临时账号
    username = f"temp_{int(time.time() * 1000)}"
    requests.post("/register/", json={...})

    # 2. 登录、改密码、验证
    ...

    # 3. 不管清理，用户名带时间戳下次不会冲突
```

### 正向验证副作用

改完密码不算完，还要**反过来验证**副作用真的生效了：

```python
# 改密码
requests.put("/me/password/", ...)

# 正向验证：用新密码能登录
resp = requests.post("/login/", json={..., "password": "新密码"})
assert resp.status_code == 200       # ← 确认密码真的被改了
```

## 五、今天踩过的坑

| 坑 | 原因 | 教训 |
|------|------|------|
| 第二次刷新 token 仍然成功 | `token_blacklist` 没注册到 `INSTALLED_APPS`，`blacklist()` 静默失败 | 配置了功能还要装对应的 app |
| 改密码用例影响 test111 | 密码真的被改了 | 有副作用操作用临时账号 |
| 第三方库返回格式不同 | SimpleJWT 不经过你的响应包装层 | 每个接口先看返回，别假设格式统一 |
