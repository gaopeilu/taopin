## 一、限流 429 → Fixture 封装

### 现象
28 个用例串行跑，每个都手动 `requests.post(login_url)`，短时间内登录太多次，触发 Django 限流 → `429 Too Many Requests`。

### 解决：用 pytest fixture 共享登录状态

**fixture 核心**：把"登录拿到 token"从每个用例里抽出来，变成可复用的资源。

### 在 conftest.py 定义 fixture

```python
@pytest.fixture(scope="module")   # ← 关键：整个文件只执行 1 次
def auth():
    resp = requests.post(f"{BASE_URL}/users/login/", json={
        "username": "test111", "password": "1234567811",
    })
    data = resp.json()["data"]
    return {
        "token": data["tokens"]["access"],     # access token
        "refresh": data["tokens"]["refresh"],   # refresh token
    }
```

### 在测试类里用

```python
class TestGetUserInfo:

    @pytest.fixture(autouse=True)   # ← 自动执行，不用每个方法写参数
    def setup(self, auth):          # ← auth 名字匹配 conftest 里的 fixture
        self.token = auth["token"]

    def test_get_user_info(self):
        resp = requests.get(url, headers={
            "Authorization": f"Bearer {self.token}"   # ← 直接用
        })
```

## 二、Scope 的四种级别

| scope | 含义 | 登录次数（28个用例） |
|------|------|:--:|
| `function` | 每个用例执行 1 次 | 28 次 → 429 ❌ |
| `class` | 每个类执行 1 次 | 8 次 → 429 ❌ |
| `module` | 每个 .py 文件执行 1 次 | 1 次 ✅ ← 目前 |
| `session` | 整个测试运行执行 1 次 | 1 次 ← 多文件项目用 |

**等写了 test_goods.py 后，改成 `session`，所有文件共享 1 次登录。**

## 三、Fixture 相关知识点全景

### 1. `@pytest.fixture` — 把函数变成可复用资源
### 2. `scope` — 控制多久执行一次
### 3. `autouse=True` — 不用每个方法显式传参，自动执行
### 4. `conftest.py` — 全局共享，同目录所有 test_*.py 自动读取，无需 import
### 5. 依赖注入 — `def setup(self, auth)`，pytest 按参数名匹配 fixture

### 关联知识（后面会用到）

| 知识点 | 一句话 | 什么时候用 |
|------|------|------|
| yield（拆解） | yield前=setup，yield后=teardown | 需要清理数据 |
| parametrize（参数化） | 一个用例跑多组数据 | 边界值测试 |
| request 对象 | 在 fixture 里获取用例名、标记等 | 动态 fixture |
| mark（标记） | @pytest.mark.smoke | 分组执行 |

### 不用 pytest 对比：你自己管全局变量

```python
_token = None

def _login():
    global _token
    if _token:                           # ← 手动判断"要不要重新登录"
        return _token
    resp = requests.post(...)
    _token = resp.json()["data"]["tokens"]["access"]
    return _token
```

fixture 就是帮做 "什么时候初始化、什么时候复用、什么时候销毁" 。

## 四、JWT：刷新 access token ≠ 杀掉旧 access token

### 现象
`test_refresh_token` 调了刷新接口，旧的 access token 没被拉黑，后续所有用例照用不误。

### 原因

```
auth fixture 登录
  └── access_token_A ✅（有效）      refresh_token_A

test_refresh_token 执行刷新
  └── access_token_B ✅（新的）      refresh_token_B（新的）
      access_token_A ✅（仍然有效！） refresh_token_A ❌（拉黑）
```

| | access token | refresh token |
|------|:--:|:--:|
| 被刷新后 | 仍然有效（直到自然过期） | 立即拉黑（不可复用） |
| 原因 | JWT 无状态，服务端无法主动废弃 | 有人为管理的 blacklist 表 |
| 拉黑条件 | 只有过期（你项目 2 小时） | 刷新即拉黑（BLACKLIST_AFTER_ROTATION=True） |

这是一个安全取舍：refresh 拉黑防凭证被盗后无限续命；access 不杀避免每次刷新全局失效所有设备。

## 五、今天踩过的坑

| 坑 | 原因 | 解决 |
|------|------|------|
| 限流 429 | 20+ 次登录串行跑 | fixture scope="module"，1 次登录 |
| scope="class" 仍 429 | 8 个类 × 1 + TestLogin 3 + 其他 = 12 次 | 改 scope="module" |
| 限流计数不清 | Django 缓存未清 | 重启 Django 服务清零 |
| conftest.py 不生效 | 文件必须和测试文件同目录或父目录 | 检查路径 |
