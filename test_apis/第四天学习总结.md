## 二、商品分类树 — 后端接口测试完整思路

### 2.1 数据结构长什么样

categories 接口返回三级树形结构，父节点带 `children` 字段，里面嵌套子节点：

```
服装 (level=1, id=1)
├── 男装 (level=2, id=5)
│   ├── T恤 (level=3, id=10, children=[])
│   └── 夹克 (level=3, id=11, children=[])
├── 女装 (level=2, id=6, children=[])
│
数码 (level=1, id=2, children=[])
```

**关键特征**：每一层结构完全一样 `{id, name, level, children, ...}`，是递归的。

### 2.2 测试树结构和测试普通列表有什么区别

| | 普通列表 | 树形结构 |
|------|------|------|
| 数据结构 | 一维数组 | 嵌套递归 |
| 断言方式 | 遍历数组逐条断言 | 递归函数遍历所有层级 |
| 核心风险 | 缺字段、排序错 | 层级颠倒、ID 重复、环形引用 |
| 数据依赖 | 不依赖其他条目 | 父子关系必须一致 |

**结论**：树结构多了一个维度——**关系一致性**，这才是测试重点。

### 2.3 测什么、不测什么

| 应该测 | 不该测 |
|------|------|
| 每节点都有 id/name/level/children | ~~断言 `data[0]["name"] == "服装"`~~ |
| id 是 int，name 非空 str，children 是 list | ~~断言一共有 3 级~~ |
| 子节点 level >= 父节点 level | ~~断言"男装"一定有 T恤和夹克~~ |
| 整棵树 ID 不重复 | ~~断言 children 长度等于几~~ |
| 不存在的 id → 404 | |
| 列表只返回顶级分类（parent=null） | |
| is_active=False 的不出现 | |
| 缺必填 → 400，无 token → 401，非商家 → 403 | |

> **原则**：测"接口契约"（字段/类型/关系/权限），不测"业务数据"（具体叫什么名字）。
> 业务数据是 seed/migration 管的，换了环境（开发/测试/生产）分类名可能不同，但字段形状必须一样。

### 2.5 递归断言 vs 硬编码层级

```python
# ❌ 硬编码层级 — 换个环境就挂
def test_three_levels(self):
    data = resp.json()["results"]
    assert data[0]["children"][0]["children"][0]["level"] == 3


# ✅ 递归断言 — 不管几层都能跑
def test_children_have_correct_level(self):
    results = resp.json()["results"]
    for parent in results:
        for child in parent.get("children", []):
            assert child["level"] >= parent["level"]
            for grandchild in child.get("children", []):
                assert grandchild["level"] >= child["level"]
```

### 2.6 前后端分工（树结构版）

| | 后端测什么 | 前端测什么 |
|------|------|------|
| 字段 | id 是 int、name 是 str | 分类名渲染在 DOM 里 |
| 层级 | children 是 list，level 逐级递增 | 缩进对齐、展开箭头显示 |
| 空子节点 | children=[] 不报错 | 不显示展开箭头 |
| 交互 | 不测 | 点击展开/收起、路由跳转 |
| icon | icon 可为 null | 有图显示图，没图显示占位 |
| 异常 | 404/401/403 | loading / error 态 |

## 三、今天踩的 4 个坑

### 坑 1：不同模块的响应格式不一样

| 模块 | 列表格式 | 详情格式 |
|------|------|------|
| users | `{code, message, data}` | `{code, message, data}` |
| goods 列表 | `{count, next, previous, results}` | N/A |
| goods 详情 | `{id, name, ...}` 直接返回对象 | N/A |
| goods tree | `[{id:1, ...}, {id:2, ...}]` 直接返回数组 | N/A |

**教训**：写断言前先 `print(resp.json().keys())` 看一眼，别假设所有接口格式一样。

### 坑 2：SPU 创建不返回 id

`GoodsSPUCreateSerializer` 的 fields 里没有 `id`，所以 POST `/goods/spus/` 返回：
```json
{"name": "xxx", "category": 1, "brand": null, ...}
```

没有 `id` 字段，导致后续 `spus/{id}/toggle_sale/` 拿不到 ID。

**解法**：创建后用 `?search=名称` 查列表拿到 ID：
```python
def _create_spu_and_get_id(token, name_prefix):
    name = f"{name_prefix}_{timestamp}"
    resp = requests.post(url, json={"name": name, ...})
    assert resp.status_code == 201
    time.sleep(0.5)
    results = requests.get(f"{url}?search={name}").json()["results"]
    return results[0]["id"]
```

### 坑 3：429 限流 — 请求太多太快

58 个用例密集执行，每个 `autouse setup` 都调一次 `categories/`，几秒内几十次请求触发 Django 限流。

**现象**：`KeyError: 'results'`，因为返回的是 `{code: 429, message: "Throttled"}`。

**解法**：模块级共享 + 类级 fixture

```python
# 1. 模块级共享数据，只查一次
_SHARED = {}


def _get_category_id():
    if "cat_id" not in _SHARED:
        resp = requests.get(f"{BASE_URL}/goods/categories/")
        _SHARED["cat_id"] = resp.json()["results"][0]["id"]
    return _SHARED["cat_id"]


# 2. 类级 fixture 替代 autouse 重复创建
@pytest.fixture(scope="class")
def spu(self, seller_auth):
    return _create_spu_and_get_id(seller_auth["token"])
```

| 之前 | 之后 |
|------|------|
| 每个用例调一次 categories → 50+ 次 | _SHARED 缓存 → 1 次 |
| autouse 每方法创建 SPU → 8 次 | scope="class" → 1 次 |
| 每秒 10+ 请求 → 限流 | 请求密度大幅降低 |

### 坑 4：`import time` 写在 fixture 里覆盖全局

在 fixture 里写了：
```python
# ❌ 错误 — 这行会创建局部变量 time，导致后续函数报 UnboundLocalError
import time

time.sleep(1)
```

`import time` 在函数体内会创建一个局部绑定，Python 编译时发现后续代码引用了 `time`，但在这个赋值之前就使用了 → `UnboundLocalError`。

**解法**：文件顶部已经 `import time` 了，fixture 里直接用 `time.sleep(1)` 就行。

## 七、坑 5 · 6：429 限流的终极解法

### 坑 5：模块间 fixture scope 不够大

**现象**：三个文件一起跑，users 里用到 `seller_auth` 的测试全挂（429）。

**原因**：`scope="module"` 只在单个 .py 文件内共享，跨文件时每个文件执行一次 login。

```
test_goods.py ──→ login seller111 ✅
test_cart.py  ──→ 没用到 seller_auth  ✅
test_users.py ──→ login seller111 ❌ 429！goods 刚登过，还没出限流窗口
```

**解法**：

```python
# conftest.py
# ❌ 之前：每个文件登一次
@pytest.fixture(scope="module")
def seller_auth():

# ✅ 之后：整个 pytest 进程只登一次
@pytest.fixture(scope="session")
def seller_auth():
```

`scope` 从小到大：

| scope | 执行次数 | 场景 |
|------|------|------|
| `function` | 每个用例 | 需要隔离的测试数据 |
| `class` | 每个类 | 类内共享的 SPU/SKU |
| `module` | 每个文件 | 文件内共享的 token |
| `session` | 全局一次 | 登录 token、数据库连接 |

**金句**：能共享就不要重复请求。

### 坑 6：限流是服务端内存计数的

**现象**：改完代码重新跑，还是 429，越跑越多。

**原因**：Django 限流计数器在服务端内存里，反复调试积累的请求没清零。**改 pytest 代码不会重置服务端计数器**。

**解法**：重启 Django 后端（`python manage.py runserver` 先停再启）。
