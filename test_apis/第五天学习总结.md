## 一、Payment 支付模块（8 用例）

### 1.1 接口与业务流

```
下单 → 发起支付(create) → 模拟支付(mock-pay) → 回调(callback) → 查询状态(status)
```

| 接口 | 方法 | 用例数 | 关键点 |
|------|------|:--:|------|
| `/payment/create/` | POST | 2 | 发起支付 / 无需登录时 401 |
| `/payment/mock-pay/` | POST | 3 | 正常支付 / 错误签名 / 越界金额 |
| `/payment/callback/` | POST | 3 | 成功 / 非法状态 / 缺参数 |
| `/payment/<no>/status/` | GET | 2 | 正常 / 无需登录 401 |

### 1.2 支付与订单的关系

- 支付模块**独立于订单模块**，有自己的 pay_no
- 支付回调会驱动订单状态从 pending → paid
- 不直接测支付宝/微信，而是测后端对支付结果的**处理逻辑**

## 二、坑 7：Reviews 评价模块的连环坑

### 坑 7-1：`_get_spu_id()` 调错了 URL

**现象**：13 个用例 8 个报 `KeyError: 'results'`

**原因**：

```python
# ❌ 错误：/goods/ 是路由根，不是 SPU 列表
resp = requests.get(f"{BASE_URL}/goods/")

# ✅ 正确：SPU 列表接口是 /goods/spus/
resp = requests.get(f"{BASE_URL}/goods/spus/")
```

**为什么之前能跑？**：之前 `/goods/` 恰好返回了可遍历的数据，后来服务端加了认证中间件，`/goods/` 直接 401 了。

**教训**：不要用「恰好能跑」的 URL，搞清楚每个接口的真实路径再调。

---

### 坑 7-2：重复评价校验 → 测试不可复跑

**现象**：第一次跑全部通过，第二次跑 `test_create_success` 报 400"您已评价过该商品"

**原因**：后端重复评价校验是 `(user, sku_id, order_no)` 三元组：

```python
# views.py 第 31 行
if Review.objects.filter(
    user=request.user, sku_id=d["sku_id"], order_no=d.get("order_no", "")
).exists():
    return Response({"code": 400, "message": "您已评价过该商品"}, status=400)
```

之前所有创建用例的 `order_no` 都是固定值（`""`、`"TEST_LIKE_001"`），第一次跑留下了数据库记录，第二次跑就冲突了。

**解法**：引入时间戳生成唯一 `order_no`：

```python
import time

def _unique_order_no(prefix="TEST"):
    """生成唯一的 order_no，避免数据库重复评价校验冲突"""
    return f"{prefix}_{int(time.time() * 1000)}"

# 用例里
"order_no": _unique_order_no(),        # test_create_success
"order_no": _unique_order_no("ANON"),  # test_create_anonymous
"order_no": _unique_order_no("LIKE"),  # test_like_success
```

**核心思想**：接口测试要做到**可复跑（idempotent）**——每次跑都能过，不依赖「数据库刚好没这条记录」。

### 坑 7-3：匿名评价和普通评价用了同一个 SKU

## 三、Search 搜索模块（9 用例）

### 3.1 接口

| 接口 | 方法 | 用例数 | 覆盖点 |
|------|------|:--:|------|
| `/search/history/` | GET | 3 | 已登录有历史 / 已登录无历史 / 未登录 |
| `/search/history/clear/` | DELETE | 2 | 正常清空 / 未登录 |
| `/search/suggest/` | GET | 4 | 带关键词 / 空关键词 / 无关键词参数 / 无结果 |

### 3.2 关键发现

搜索建议接口**不强制登录**，但已登录用户的搜索会记录到历史：

```python
def test_suggest_records_history(self, auth):
    """已登录用户的搜索会记录到历史"""
    token = auth["token"]
    # 先执行搜索
    requests.get(
        f"{BASE_URL}/search/suggest/?q=手机",
        headers={"Authorization": f"Bearer {token}"},
    )
    # 再查历史
    resp = requests.get(f"{BASE_URL}/search/history/", headers={...})
    keywords = [h["keyword"] for h in resp.json()["data"]]
    assert "手机" in keywords
```

**测试要点**：验证了「搜索」和「搜索历史」两个接口的**隐式联动**——不是代码显式调用，而是数据库层面的数据流转。

## 四、Orders 发货用例补完

### 4.1 `test_ship_not_owner`：商家发货他人商品 → 403

```python
def test_ship_not_owner(self):
    """seller111 尝试发别人的货"""
    # 创建订单（SKU_ID=18 属于 seller=2）
    resp = _create_order(self.token)
    order_no = resp.json()["data"]["order_no"]

    # 支付
    requests.post(f"{BASE_URL}/orders/{order_no}/pay/", ...)

    # seller111 发货 → 应被拒绝
    resp = requests.post(
        f"{BASE_URL}/orders/{order_no}/ship/",
        json={"express_no": "SF123456"},
        headers={"Authorization": f"Bearer {self.seller_token}"},
    )
    assert resp.status_code == 403
    assert "您不是该订单商品的卖家" in resp.json()["message"]
```

**价值**：权限不是「你是商家就能发货」，而是「你是**这个订单对应商品所属店铺**的商家才能发货」——细粒度权限验证。

### 4.2 `test_ship_success` 加了前置跳过

```python
def test_ship_success(self):
    # 检查 seller111 是否拥有 SPU
    resp = requests.get(f"{BASE_URL}/goods/spus/?seller=me", headers=...)
```

**思想**：测试不应该因为环境数据不全而**报错**，应该**跳过**并给出明确原因。

## 五、坑 8：`test_create_insufficient_stock` quantity=99999

**现象**：`assert '库存不足' in "items: {'quantity': [ErrorDetail(string='Ensure this value is less than or equal to 999.', code='max_value')]}"}`

**原因**：quantity=99999 先被 DRF 的 `IntegerField(max_value=999)` 拦截了，根本没走到业务层"库存不足"的校验。

**解法**：quantity 改成 999（通过 DRF 校验但超过库存 188）

```python
# ❌ 99999 被 DRF 框架层拦截
"items": [{"sku_id": SKU_ID, "quantity": 99999}]

# ✅ 999 通过框架层，到达业务层，返回"库存不足"
"items": [{"sku_id": SKU_ID, "quantity": 999}]
```

**教训**：异常测试要确认错误的**来源**——是框架层拦截还是业务层拦截，两者的错误信息完全不同。

## 六、坑 9：全量跑 429 Too Many Requests

**现象**：单独文件全过，200+ 用例一起跑约有 15% 报 429

**原因**：`settings.py` 配置了匿名用户限流 60次/分钟：

```python
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_CLASSES": [
        "rest_framework.throttling.AnonRateThrottle",
    ],
    "DEFAULT_THROTTLE_RATES": {
        "anon": "60/minute",
    },
}
```

200+ 用例中有部分不发 token 的请求（搜索建议、商品列表等），累计超了 60 次。

### 解法：DEBUG 模式放宽容忍度

```python
# settings.py
if DEBUG:
    REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]["anon"] = "1000/minute"
```

**只在本地开发生效**，生产环境 `DEBUG=False` 保持原来的 60/min。

## 七、工程化思考

### 7.1 当前框架离企业级的差距

| 维度 | 当前状态 | 差一步就到 |
|------|---------|----------|
| 环境管理 | BASE_URL 硬编码 | 环境变量可切换（dev/staging/prod） |
| 测试报告 | pytest 裸跑 | Allure 可视化报告 + 历史趋势 |
| 分级执行 | 全量一起跑 | smoke（<3min）/ regression 标签 |
| CI/CD | 手动跑 | GitHub Actions 提交即测 |
| 数据隔离 | 依赖已有数据 | 用例自建数据 + teardown 清理 |
| 并发测试 | 未涉及 | ThreadPoolExecutor 模拟并发 |
| Schema 校验 | 手写断言 | jsonschema / pydantic 自动校验 |

### 7.2 缺的测试维度

| 优先级 | 维度 | 示例 |
|:--:|------|------|
| 🔴 | 并发安全 | 并发下单(超卖)、并发领券(超发)、并发注册 |
| 🟡 | 幂等性 | 重复支付、回调重放 |
| 🟡 | 数据一致性 | 取消订单恢复库存、改密码后旧 token 失效 |
| 🟢 | 安全 | 搜索 XSS/SQL 注入 |
| 🟢 | 边界值 | 分页 page_size=0、数量负数 |

### 7.3 并发测试工具选型

| 场景 | 工具 | 复杂度 |
|------|------|:--:|
| 接口并发正确性（2-5 并发测逻辑） | `concurrent.futures.ThreadPoolExecutor` | ⭐ |
| 负载压测（200+ 并发测性能） | Locust | ⭐⭐ |
| 传统企业压力测试 | JMeter | ⭐⭐⭐ |

**区别**：
- 并发正确性：测"两个请求同时来，会不会创两条数据"→ pytest 用例
- 负载压测：测"200 人同时下单，系统扛不扛得住"→ 专用工具

## 八、核心收获

### 技术层面

1. **URL 要精确**：`/goods/` ≠ `/goods/spus/`，别靠"恰好能跑"
2. **order_no 要唯一**：数据库有唯一约束时，用例必须每次生成不同的值
3. **quantity 要注意框架拦截层**：先过 DRF 校验再过业务校验，断言要匹配正确的错误来源
4. **店铺级权限**：商家≠该商品的商家，发货要验证归属
5. **pytest.skip 代替报错**：环境数据不全时跳过，不要报 FAIL

### 思想层面

6. **可复跑性（Idempotency）**：测试跑 10 次应该 10 次都通过，不能依赖数据库的初始状态
7. **测试分层**：功能测试 / 并发正确性测试 / 负载压测，三种场景三种工具
8. **工程化最后一公里**：写完测试只是 60%，CI + 报告 + 通知才是 100%
