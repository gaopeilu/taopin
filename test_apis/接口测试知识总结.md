# 接口测试知识总结

> 基于淘拼商城项目，从零写接口测试的过程中踩过的坑和搞懂的概念。

---

## 一、追查接口行为的四步法

以后遇到任何接口，按这四步查，5 分钟确定完整行为：

```
你的测试请求
    │
    ▼
① urls.py ──→ 匹配到哪个 View 的哪个方法？
    │
    ▼
② views.py ──→ serializer.is_valid(raise_exception=True) 还是手动 if/else？
    │              │
    │              ├── 校验失败 → ③ raise ValidationError → ④ exceptions.py → 返回
    │              │                                              │
    │              │                              ┌── 字符串 → 只有 message
    │              │                              └── 字典   → message + errors
    │              │
    │              └── 校验通过 → 继续往下 → return Response({...}, status=???)
    │                                                      ↑
    │                                              看这里 = 成功状态码
```

### 具体步骤

| 步骤 | 看什么 | 找什么 |
|------|--------|--------|
| ① | `dianshang/urls.py` → `apps/xxx/urls.py` | URL 匹配到哪个 View |
| ② | `apps/xxx/views.py` | `serializer.is_valid()` 还是手动判断 |
| ③ | `apps/xxx/serializers.py` 的 `validate()` | 搜 `raise ValidationError`，每个 raise 就是一个异常场景 |
| ④ | `utils/exceptions.py` | 错误响应最终是什么格式 |

## 二、HTTP 状态码 vs 业务 code

它们不在同一个位置，是两层不同的东西：

```
HTTP 响应
│
├── 状态行:  HTTP/1.1 201 Created    ← HTTP 状态码（resp.status_code）
│
└── 响应体:  {
                "code": 200,          ← 业务 code（resp.json()["code"]）
                "message": "注册成功",
                "data": {...}
            }
```

### 对比表

| | HTTP 状态码 | 业务 code |
|------|------------|-----------|
| 位置 | 响应头第一行 | JSON body 里 |
| 断言 | `resp.status_code` | `resp.json()["code"]` |
| 谁定义 | HTTP 协议规范 / DRF 框架 | 你自己在代码里写 |
| 作用 | 快速分诊（哪些请求挂了） | 精确定位（什么原因） |
| 成功时的值 | 200 或 201 | 通常 200 |
| 失败时的值 | 通常是 400 | 跟着 HTTP 或自定义（如 10001） |

### 实际例子

```
注册成功:  HTTP 201  +  body code: 200    ← 成功时不一样
登录成功:  HTTP 200  +  body code: 200    ← 没写 status= 时一样
密码错误:  HTTP 400  +  body code: 400    ← 失败时通常一样
```

## 三、谁决定状态码

| 情况 | 谁决定的 | 示例 |
|------|----------|------|
| 校验失败 `ValidationError` | **DRF 框架自动给 400** | 序列化器校验不通过 |
| View 里手动写了 `status=xxx` | **你自己** | `status=status.HTTP_201_CREATED` |
| View 里没写 `status=` | **DRF 默认 200** | `return Response({...})` |

### 总结

```
HTTP 状态码:  你可以自己写，不写的话 DRF 给默认值（成功=200，校验失败=400）
业务 code:    你自己写在 JSON body 里，不写就没有
失败时两者一样:  这个项目的习惯，不是硬性规定，完全可以不一样
```

## 四、ValidationError 的两种写法（影响响应格式）

这是最容易踩的坑。`ValidationError` 的参数类型直接决定响应有没有 `errors` 字段：

### 字典类型 → 有 message + errors

```python
# serializers.py
raise serializers.ValidationError({"password_confirm": "两次密码不一致"})
```

响应：

```json
{
    "code": 400,
    "message": "password_confirm: 两次密码不一致",
    "errors": {
        "password_confirm": ["两次密码不一致"]
    }
}
```

### 字符串类型 → 只有 message，没有 errors

```python
# serializers.py
raise serializers.ValidationError("用户名或密码错误")
```

响应：

```json
{
    "code": 400,
    "message": "用户名或密码错误"
}
```

### 断言口诀

```
先看 serializers.validate() 里 ValidationError 的参数：
  - 传字典 → 断言 "errors" in json_data
  - 传字符串 → 不要断言 errors，只有 message
```

## 五、异常处理的三层链路

```
① serializers.py
   raise ValidationError("xxx")
        │
        ▼
② DRF 框架（自动）
   HTTP 400 + {"detail": "xxx"}
        │
        ▼
③ utils/exceptions.py（你定义的）
   重新打包成 {"code": 400, "message": "xxx"}
```

**关键文件**：

| 文件 | 作用 |
|------|------|
| `apps/xxx/serializers.py` | 定义校验规则和错误消息 |
| `utils/exceptions.py` | 统一包装错误响应格式 |
| `utils/response.py` | 定义了 `success_response` 和 `error_response` 模板（项目里大多没用） |

## 六、写测试用例的标准套路

### 每个接口至少写两类

| 类型 | 说明 |
|------|------|
| 正常用例 | 合法参数，断言成功响应 |
| 异常用例 | 去 serializers 搜 `raise ValidationError`，每个 raise 一个用例 |

### 每个用例断言三件事

```python
# 1. HTTP 状态码
assert resp.status_code == 200

# 2. 业务 code
json_data = resp.json()
assert json_data["code"] == 200

# 3. 关键 data 字段
assert "tokens" in json_data["data"]
```

### 测试数据避免冲突

```python
import time

timestamp = int(time.time() * 1000)
username = f"test_{timestamp}"
phone = f"138{timestamp % 100000000:08d}"
```

## 七、企业级数据清理方案

| 方案 | 适用场景 |
|------|----------|
| 时间戳动态数据 | 最简单，适合单人学习项目 |
| 独立测试库 + 事务回滚 | pytest-django 单元测试 |
| API 生命周期闭环 | 创建什么就通过 API 删除什么 |
| UUID + 定期清理脚本 | 大厂常见，定时清 `autotest_` 前缀数据 |
